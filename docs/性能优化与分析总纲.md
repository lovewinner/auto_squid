## 一、一句话定位

auto_squid 是一个**正向 HTTP/HTTPS 代理**：监听一个端口，客户端把流量交给它，它在一组上游 Squid 代理上做**并行竞速**（Happy Eyeballs 思路），谁先成功就用谁；并对"域名 → 最优代理"做缓存复用，兼顾"快"与"稳"。

**核心价值主张**：多个上游代理的可用性、速度、地区分布各不相同。竞速（race）能在**无需任何先验质量模型**的情况下自动选中最快的可用代理；域名缓存 + 会话粘性把竞速结果沉淀为"稳态最优路径"。

## 二、当前架构与请求链路

### 2.1 模块划分

| 模块 | 职责 |
|---|---|
| `auto_squid/router.py` | 全部转发引擎：竞速、域名/响应/粘性三级缓存、连接池、熔断/探活、统计持久化 |
| `auto_squid/api.py` | FastAPI 管理 API + 单页 Web 仪表盘（含内联 HTML/JS） |
| `auto_squid/config_schema.py` | pydantic 配置模型（listen/api/router/logging + ProxyInfo） |
| `auto_squid/cli.py` | Typer 入口：加载配置 → 起 Router + uvicorn API → 优雅关闭 |
| `auto_squid/auth.py` | 客户端 HTTP Basic 认证 |
| `auto_squid/proxy_store.py` | 上游代理注册表（YAML 加载/保存 + 内存 CRUD） |

辅助：`bench/`（压测工具链）、`tests/test_end_to_end.py`（133 用例）。

### 2.2 请求处理流程

```
客户端 ──HTTP/S──> :10808 handle_client
                      │  解析首行+头 → 可选认证(407) → 按 CONNECT/HTTP 分流
                      ▼
              _handle_http_request / _handle_connect
                      │
        ┌─────────────┴──────────────────────────────┐
        ▼                                            ▼
   HTTP: 响应缓存 → 在途GET聚合 → 会话粘性 → 域名缓存 → 竞速
                                              CONNECT: 会话粘性 → 域名缓存 → 竞速
        │                                            │
        ▼                                            ▼
   _forward_single（流式转发+边收边缓冲缓存）      _relay_tunnel（双向裸管道透传）
        │
        ▼
   胜者回写 _record_win_meta（域名缓存）+ _record_sticky（粘性表）
```

### 2.3 三级缓存决策树（HTTP 路径）

| 优先级 | 机制 | 键 | 命中动作 | TTL |
|---|---|---|---|---|
| 1 | **HTTP 响应缓存** | `GET:<url>` | 整包回写（完全不经上游） | 60s（尊重 Cache-Control） |
| 1.5 | 在途 GET 去重聚合 | `GET:<url>` | 并发同 URL 请求 await 首请求结果（防 cache stampede） | 0.1s 等待超时 |
| 2 | **会话粘性** | `client_ip\|domain` | 该代理单发（不竞速），egress IP 稳定 | 1800s 滑动（命中刷新） |
| 3 | **域名缓存** | `domain` | 该代理单发 | 600s（自适应 TTL 时按稳定度浮动） |
| 4 | 竞速 | — | 首批 `max_retries` 个并行（错峰则先发最优），首字节判胜 | 每次请求 |

## 四、可参考的技术/算法（带出处）

> 均为 2026-08 复核的一手文献；是以上优化点的理论依据。链接见文末。

### 4.1 Happy Eyeballs 竞速排序与错峰（RFC 8305）

- §4 排序：有状态客户端应维护每个候选的历史 RTT，**按 RTT 从低到高排序**后再竞速 → 先发的更可能先赢，减少扇出。
- §4 关键约束：**历史 RTT 数据不可跨网络接口/网络切换沿用**，换网络应清空。
- §5 错峰：连接尝试**不应同时发起**。默认连接尝试延迟 **250ms**，下限 **100ms**（绝对值下限 10ms，防丢包率高时拥塞崩溃），上限 **2s**。

**→ 已在 auto_squid 落地**：EWMA 排序（P1-1）、错峰启动（P1-2）、`POST /quality/reset` 换网络清空。

### 4.2 EWMA / peak-EWMA 质量模型（Finagle/Linkerd 实验）

**实验结论**（11 后端、单节点人为变慢到 2s 30 秒）：
| 算法 | 能扛住的尾延迟分位 | 1s 超时换算成功率 |
|---|---|---|
| round-robin | ~95 分位 | ~95% |
| least-loaded（在途最少） | ~99 分位 | ~99% |
| **peak-EWMA**（RTT 移动平均 × 在途数） | **~99.9 分位** | **~99.9%** |

**→ 已在 auto_squid 落地**：EWMA 排序（P1-1）+ in-flight 加权 `ewma × (1+active)^lb_bias`（P2-1），即 peak-EWMA 的对偶。

### 4.3 P2C（Power of Two Choices）+ 加权 least-request（Envoy/Dubbo）

- **P2C**：每次随机抽 2 个，选在途更少的。复杂度 O(1)，抗"羊群效应"（herding）。
- **加权 least-request**（Envoy `LeastRequest`）：`有效权重 = 静态权重 / (在途数 + 1)^bias`（bias 默认 1.0）。在途多的代理权重被压低。
- **Dubbo**：默认加权随机，官方文档点名缺陷——**慢代理会堆积请求**。

**→ 已在 auto_squid 落地**：排序权重 `ewma × (1+active)^lb_bias`（P2-1），同权重段随机打乱保留抗羊群。

### 4.4 熔断 / 异常点检测 / 慢启动（Envoy outlier / Hystrix）

- **熔断器**：连续失败 N 次 → 打开电路，退避期内不参与竞速；后台探活恢复后放回（指数退避探测）。
- **outlier detection**：consecutive_5xx / success_rate / failure_percentage 等维度触发剔除。
- **slow-start**：新加入或熔断恢复的代理从低权重开始，随成功次数在窗口内爬升（Envoy 默认 60s）。

**→ 已在 auto_squid 落地**：熔断器 + 指数退避（P1-3）、slow-start 垫底爬升（P1-3）、单发降级（P2-5）。

### 4.5 自适应并发限制（Netflix / Envoy）

动态调整每个上游允许的在途请求数（加性增、乘性减，基于延迟梯度）。

**→ 已在 auto_squid 落地**：`router.concurrency_limit`（P3-3）。

### 4.6 一致性哈希（Envoy ring hash / Maglev）

若希望"同一资源稳定映射到同一代理"（跨重启/跨进程稳定）。Maglev 查表/建表比 Ketama 快约 5-10 倍，但增删节点扰动约 2 倍。

**→ 未实施**（P3-2），当前由会话粘性提供同客户端+域名稳定。

### 4.7 域名/资源 → 代理子集的策略路由（PBR / SD-WAN rule）

按目标特征收窄候选集：`域名模式 → 代理子集`，竞速只在该子集内进行。

**→ 已在 auto_squid 落地**：`router.policies`（P1-5）。

## 六、未实施项详情与建议

### 6.1 一致性哈希稳定映射（P3-2）⬜

- **适用场景**：需要跨重启/跨进程 egress 映射稳定（同一域名始终走同一代理，即使该代理的 EWMA 不是当前最快）。
- **张力**：与"追求最快"目标冲突。当前 `会话粘性`（per-client+domain）已提供同客户端稳定，但重启后粘性表清空、且不同客户端可映射到不同代理。若业务要求"域名 → 单一出口"（如源站对出口 IP 白名单），一致性哈希才有价值。
- **若实施**：Maglev 建表/查表比 Ketama 快（Envoy 基准），但增删节点扰动约 2 倍；表大小可调。

### 6.3 置信度驱动的竞速 vs 单发（P3-4）⬜

- UCB/ε-greedy 形式化 `recheck_hits`：对不确定域多试、对稳定域少试。
- 原分析即评估收益有限（HTTP 败者首字节即取消，竞速边际成本不高）。
- 当前已有 `recheck_hits`（周期重竞速）+ `single_send_degrade`（质量感知降级）覆盖大部分需求，此项优先级最低。

### 6.4 systemd unit（O-1）⬜

- 当前仅 docker-compose。若部署不依赖容器，补一个 `auto_squid.service`（`ExecStart=/path/to/.venv/bin/python -m auto_squid.cli`，Restart=on-failure，配合 `config.yaml`/`proxies.yaml` 路径）。

### 6.5 真实 Squid 集成测试 / CI（O-2、O-3）⬜

- bench 已支持 `--upstream real`，可手动对真实 Squid 跑。缺自动化 CI。
- 建议 `.github/workflows/ci.yml`：`uv sync && pytest -q`，跑完 bench mock 冒烟。

### 6.6 管理 API TLS / token（O-4）⬜

- 已实现 HTTP Basic（`api.auth`），但凭据经 HTTP 明文传输。若管理 API 暴露到非可信网络，建议加 TLS（uvicorn `--ssl-keyfile/--ssl-certfile`）或前端反代 TLS。

## 七、压测与验收指标

建议每次优化都至少跑三组：

```bash
python -m bench.stress --quick --rounds 3
python -m bench.stress --mode mixed --rounds 3
python -m bench.stress --mode soak --duration 120 --rounds 3
```

若有真实上游代理：

```bash
python -m bench.stress --upstream real --proxies proxies.yaml --mode mixed --duration 120 --rounds 3
```

核心指标：

| 指标 | 目标 |
| --- | --- |
| TTFB P50/P95/P99 | 下降，尤其是 P95/P99 |
| total latency P95/P99 | 不能因后台清理、缓存或 fd 压力变差 |
| `racing.amplification` | 下降；CONNECT 场景越低越好 |
| `upstream_attempts` | 在成功率不下降的前提下降低 |
| `domain_hit_rate` / `sticky_cache_hits` | 热域名和稳定会话应上升 |
| `http_hit_rate` | 对可缓存 GET 应上升 |
| `proxy_in_flight` / `max_in_flight` | 不应长期集中在慢代理 |
| `circuit_open_count` | 坏代理场景应增长；正常场景不应频繁增长 |
| `probes_skipped` | 长期增长说明 canary 不合适 |
| server loop lag P95/max | 不应显著上升 |
| RSS / fd_peak | soak 下应稳定 |

## 八、代码级注意事项

- 被竞速取消的候选不能记失败，否则健康慢代理会被误熔断。当前 `_try_http()` / `_try_tunnel()` 已处理，后续改动要保留。
- 竞速赢家只应在确认采用后更新域名 meta，败者只能记 attempted stats。当前 `_record_win_meta()` 的调用位置是正确的。
- 单发降级与熔断要解耦：降级是"不要继续确定性单发"，熔断是"暂时剔除候选"。
- 策略路由必须同时作用于粘性、域名缓存和竞速，否则旧缓存可能绕过新策略。
- HTTP 缓存 LRU 必须同步维护 `_http_cache_domain_index`，否则写方法按域名失效会漏删。
- CONNECT 预热池必须有全局 fd 预算和 per-proxy 上限，不能为了降低 TTFB 引入资源泄漏。两阶段池（`_conn_pool` + `_target_pool`）**共享** `conn_pool.total` 预算，改任一建连处都要同时计入另一池（`_conn_pool_refill` 与 `_target_pool_refill` 均已计入）；空闲超时统一由 `_pool_prune` 周期清理。
