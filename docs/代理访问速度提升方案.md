# auto_squid 代理访问速度提升方案

> 日期：2026-08-08  
> 代码版本：HEAD `4c3be8e`  
> 范围：`auto_squid/router.py`、`config_schema.py`、`cli.py`、`api.py`、`bench/`  
> 目标：降低代理访问 TTFB、减少无效上游请求扇出、提升高并发和坏代理场景下的稳定性。

## 1. 结论摘要

当前项目已经不是简单随机代理转发器，而是一个具备较完整速度优化能力的正向代理：

- HTTP 走 `httpx.AsyncClient` 长驻连接池，每个上游一个池，复用 keep-alive。
- CONNECT 走裸 `asyncio.open_connection` 隧道，竞速后双向 pipe。
- 请求路径按 `HTTP 响应缓存 -> 在途 GET 聚合 -> 会话粘性 -> 域名缓存 -> 竞速` 决策。
- 竞速已支持 EWMA 首字节延迟排序、错峰启动、失败熔断、后台 CONNECT 探活、slow-start、in-flight least-request 排序。
- 热路径统计和域名元数据走内存镜像，SQLite 后台批量 flush，避免逐请求 fsync。

所以后续提速的重点不是“加一个竞速”，而是：

1. 调好已有能力，让真实部署默认走质量感知路径。
2. 补齐按目标/地域收窄候选集，避免把明显不合适的代理拿来竞速。
3. 降低 CONNECT 建链成本，尤其是域名缓存过期、冷启动和代理故障恢复时。
4. 用压测指标闭环，而不是只看单次 curl 体感。

## 2. 当前访问链路分析

### 2.1 HTTP 请求链路

入口在 `Router.handle_client()`：

1. 读取首行和请求头，可选执行客户端 Basic 认证。
2. 普通 HTTP 请求解析 method、url、headers、body。
3. 进入 `_handle_http_request()`：
   - `GET` 先查内存响应缓存 `_http_cache`。
   - 同 URL 并发 GET 通过 `_inflight_futures` 聚合，等待 100ms，避免缓存击穿。
   - 写方法按域名清空 GET 缓存，防止返回旧内容。
4. 进入 `_forward_upstream()`：
   - 会话粘性命中则单发。
   - 域名缓存命中则单发。
   - 未命中则走 EWMA 排序后的错峰竞速。
5. `_stream_upstream_response()` 流式转发响应体，同时在 1MiB 上限内缓冲可缓存响应。

速度关键点：

- 响应缓存命中时不访问上游，是最快路径。
- 粘性/域名缓存命中时跳过竞速，只打一条上游链路。
- 竞速路径以“响应头到达”判胜，body 不阻塞 TTFB。
- 败者清理下放后台，避免阻塞赢家首字节。

### 2.2 CONNECT 请求链路

CONNECT 入口在 `_handle_connect()`：

1. 优先走会话粘性单发。
2. 再走 `target(host:port)` 维度的域名缓存。
3. 未命中时对上游代理做 CONNECT 竞速。
4. 赢家回写 `200 Connection established`，随后 `_relay_tunnel()` 双向透传。

速度关键点：

- CONNECT 没有响应缓存，主要依赖粘性、域名缓存、EWMA 排序和错峰减少建链。
- CONNECT 败者的成本高于 HTTP 败者：隧道建好再关浪费更明显。因此错峰启动对 CONNECT 的收益很大。
- 当前 CONNECT 的上游裸 socket 不复用，每次隧道都要新建到上游代理的 TCP 连接。这是后续可优化点。

## 3. 已有速度优化能力

| 能力 | 位置 | 作用 |
| --- | --- | --- |
| 上游连接池 | `_get_client()` | HTTP 请求复用到上游代理的 keep-alive 连接，减少 TCP/代理握手 |
| EWMA 排序 | `ProxySelector.record_ttfb()` / `ordered_proxies()` | 历史 TTFB 小的代理优先参与竞速 |
| 错峰启动 | `_race_staggered()` | 先发最优候选，间隔补发，减少 HTTP 双写和 CONNECT 扇出 |
| 熔断器 | `record_failure()` / `is_circuit_open()` | 连续失败代理在退避期内不参与单发/竞速 |
| 后台探活 | `_probe_loop()` / `_probe_proxy()` | 低流量时也能更新代理可达性和 EWMA |
| slow-start | `_in_slow_start()` | 熔断恢复代理先低权重试水，避免恢复即被打满 |
| in-flight 惩罚 | `_weighted_rank()` | 排序权重为 `ewma * (1 + active)^lb_bias`，避开积压代理 |
| 域名缓存 | `_get_fresh_proxy()` | 同域名复用赢家，减少重复竞速 |
| 会话粘性 | `_get_sticky_proxy()` | 同客户端+域名复用出口，减少选路抖动 |
| 单发降级 | `_single_send_degraded()` | 钉住代理失败或 EWMA 恶化时回退竞速 |
| GET 响应缓存 | `_http_cache_get()` / `_http_cache_set()` | 幂等小响应直接内存返回 |
| GET 聚合 | `_inflight_futures` | 同 URL 并发 miss 只让首个请求回源 |
| SQLite 后台落盘 | `_flush_loop()` | 热路径只写内存，周期批量持久化 |
| uvloop | `cli.py` | 降低 asyncio 调度和 socket I/O 开销 |

## 4. 主要瓶颈和风险点

### 4.1 示例配置未暴露关键调参项

`config_schema.py` 已有 `stagger_start`、`stagger_initial`、`stagger_interval_ms`、`router.circuit.*`，但 `examples/config.yaml` 只展示了基础字段和 stickiness，没有展示 circuit 与错峰配置。

影响：

- 运维不知道如何开启单发降级，默认 `single_send_degrade_*` 是关闭状态。
- 探活 canary、熔断阈值、least-request bias 无法通过示例形成部署习惯。
- 真实环境若 `1.1.1.1:443` 不可达，探活会被跳过，质量模型主要依赖真实请求。

### 4.2 CONNECT 无上游连接复用

HTTP 路径有 `httpx` 池化，但 CONNECT 竞速和单发都通过裸 `asyncio.open_connection(proxy.host, proxy.port)` 新建到上游代理的 TCP 连接。

影响：

- HTTPS 流量占比高时，每条隧道至少多一次“本机 -> 上游代理”建连。
- 域名缓存/粘性命中虽然减少竞速，但不能减少 CONNECT 到上游的建连成本。
- 高并发短连接 HTTPS 场景下，fd 和端口复用压力更高。

### 4.3 策略路由尚未启用

`ProxyInfo.tags` 已预留，但当前 `ordered_proxies()` 对所有 enabled 代理排序，不按目标域名、地域、业务类型收窄候选集。

影响：

- 国内目标、海外目标、流媒体、API、下载等不同流量会在同一代理池里竞速。
- 代理有地域/成本/带宽差异时，EWMA 只能事后学习，无法利用先验规则直接排除明显不合适的候选。

### 4.4 HTTP 响应缓存容量无全局上限

单条响应缓存 body 上限是 1MiB，TTL 是 60s，但 `_http_cache` 没有条目数或总字节上限。

影响：

- 高基数 URL 短时间涌入时，60s 内可能累积大量小对象。
- 内存压力上升后会拖慢 Python GC 和整体事件循环。

### 4.5 域名缓存 TTL 是全局固定值

`cache_ttl` 全局默认 600s，所有域名同一过期策略。

影响：

- 稳定域名可以更久单发，减少竞速。
- 抖动域名应该更短 TTL 或更频繁重评估。
- 当前只能通过单发降级和粘性 recheck 局部修正，缺少“按稳定度自适应 TTL”。

### 4.6 探活目标单一

后台探活只 CONNECT 到一个 `probe_canary`。代码已经做了本机直连可达性预检，不可达时跳过整轮，避免误熔断。

影响：

- 单 canary 不能覆盖不同地域代理到不同目标网络的质量差异。
- canary 被限流、路由异常或策略阻断时，探活价值下降。

## 5. 优化方案

### P0：立即配置优化

这是不改代码即可做的方案。

建议生产配置显式写出以下字段：

```yaml
router:
  max_retries: 3
  cache_ttl: 600
  stagger_start: true
  stagger_initial: 1
  stagger_interval_ms: 250
  stickiness:
    enabled: true
    ttl: 1800
    recheck_hits: 100
    max_entries: 100000
  circuit:
    probe_interval_sec: 30
    probe_canary: "1.1.1.1:443"
    circuit_threshold: 3
    circuit_max_backoff: 300
    slow_start_window: 60
    slow_start_success: 3
    lb_bias: 1.0
    single_send_degrade_fail: 2
    single_send_degrade_ratio: 3.0
    single_send_degrade_slack_ms: 10
```

调参建议：

- HTTPS/CONNECT 占比高：保持 `stagger_start=true`，`stagger_initial=1`，优先减少无谓隧道。
- 代理质量波动大：开启 `single_send_degrade_fail=2`、`single_send_degrade_ratio=3.0`，让域名缓存和粘性更快回退竞速。
- 高并发压力大：保持 `lb_bias=1.0`；如果发现最快代理被过度避让，可降到 `0.5`；如果慢代理容易积压，可升到 `1.5`。
- 探活 canary 必须选本机和上游都能稳定访问的目标。部署后看 `/circuit`，如果 `probes_skipped` 持续增长，说明 canary 不适合当前网络。

### P1：补齐配置示例和运行手册

修改 `examples/config.yaml`，完整展示 `stagger_*` 与 `router.circuit`。同时在 README 中增加“速度相关配置推荐”。

收益：

- 降低部署误用概率。
- 让已有优化真正进入生产配置。
- 便于压测时记录和复现实验条件。

验收：

- `examples/config.yaml` 包含所有当前 `RouterConfig` 和 `CircuitConfig` 字段。
- README 给出“稳定优先”“速度优先”“低扇出优先”三套参数建议。

### P1：策略路由，按目标收窄代理候选集

新增策略配置，例如：

```yaml
router:
  policies:
    - match:
        domain_suffix: [".cn", "baidu.com", "qq.com"]
      proxies:
        tags:
          region: "cn"
    - match:
        domain_suffix: ["youtube.com", "google.com"]
      proxies:
        tags:
          region: "hk"
    - match:
        domain_regex: ".*\\.api\\.example\\.com$"
      proxies:
        ids: ["proxy-a", "proxy-b"]
```

实现思路：

1. 扩展 `config_schema.py`，增加 `PolicyConfig`。
2. `ProxyInfo.tags` 已存在，可直接用于地域、线路、成本、带宽标记。
3. 在 `_forward_upstream()` 和 `_handle_connect()` 进入竞速前，根据 domain/target 过滤 `selector.ordered_proxies()` 的结果。
4. 域名缓存和粘性取用时也要校验当前代理仍满足策略，不满足则视为 miss。

收益：

- 减少不必要竞速候选，直接降低 TTFB 和 upstream_attempts。
- 避免错误地域出口导致源站慢、被风控或不可达。
- 对代理池异构程度越高，收益越明显。

验收指标：

- `/metrics` 中 `racing.amplification` 下降。
- 真实上游模式下，目标站状态码中 502/503/timeout 降低。
- 同一目标域的 EWMA 收敛更快，域名缓存命中率上升。

### P1：CONNECT 上游连接复用或隧道预热

当前 CONNECT 每次新建到上游代理的 TCP 连接。可以分两阶段做：

第一阶段：上游代理 TCP 连接预热池。

- 为每个上游维护少量空闲 TCP 连接。
- CONNECT 请求到来时优先取已连接到代理的 socket，再发送 CONNECT target。
- 隧道结束后该连接不能复用到新 target，因为 CONNECT 后 socket 已被隧道占用并随会话关闭；但预热池可以提前补充下一条空闲代理连接。

第二阶段：按热点 target 做半预连接谨慎试验。

- 对高频 CONNECT target，在域名缓存或粘性命中时提前建立“到上游代理”的 TCP，而不是提前 CONNECT 到目标。
- 避免真正打到源站前产生多余连接。

收益：

- 降低短 HTTPS 连接的建链 TTFB。
- 高并发场景减少连接建立尖峰。

风险：

- 预热连接占 fd，需要 per-proxy 上限、空闲超时、全局 fd 预算。
- 部分上游代理会主动关闭空闲连接，取用时需健康检查。

验收：

- `bench --mode conn-reuse` 增加 CONNECT 类场景。
- 对比 CONNECT TTFB P50/P95/P99 和 fd_peak。

### P2：HTTP 缓存增加总容量和 LRU 淘汰

新增参数：

```yaml
router:
  http_cache:
    enabled: true
    ttl: 60
    max_entries: 10000
    max_bytes: 268435456
    stream_cache_limit: 1048576
```

实现思路：

- 将 `_http_cache` 从普通 dict 改为 `OrderedDict` 或维护访问时间。
- `_http_cache_set()` 前检查 `max_entries` 和 `max_bytes`，淘汰最久未访问条目。
- `_http_cache_get()` 命中时更新 LRU 顺序。
- `_http_cache_domain_index` 同步删除淘汰条目。

收益：

- 高基数 URL 下控制内存，避免 GC 拖慢事件循环。
- 可按机器内存调大缓存，用内存换 TTFB。

验收：

- `/metrics` 增加 `http_cache_bytes`、`http_cache_evictions`。
- soak 压测中 RSS 不随 URL 基数无界增长。

### P2：自适应域名缓存 TTL

当前 `cache_ttl` 是全局固定值。可以让每个域名根据稳定度调整 TTL：

- 连续由同一代理获胜，且 EWMA 方差低：TTL 逐步增加，例如 600s -> 1800s。
- 单发降级、5xx、熔断、recheck 换赢家：TTL 降低，例如回到 60s。
- 域名策略命中强规则时可使用更长 TTL。

收益：

- 稳定域名减少竞速和重评估。
- 抖动域名更快换路，降低长时间钉住慢代理的风险。

验收：

- `/domains/meta` 展示每域名 `ttl`、`expires_at`、`switch_count`。
- 热域名 `racing_invocations` 减少，且故障切换时间不变差。

### P2：多 canary 探活和按标签探活

支持配置多个探活目标：

```yaml
router:
  circuit:
    probe_interval_sec: 30
    probe_canaries:
      - name: "global"
        target: "1.1.1.1:443"
      - name: "cn"
        target: "www.baidu.com:443"
        tags:
          region: "cn"
```

实现思路：

- 每个代理按 tags 选择合适 canary。
- EWMA 质量表可保留全局 EWMA，同时记录 per-canary 质量。
- 策略路由命中时优先使用同标签质量。

收益：

- 让探活更接近真实目标网络。
- 减少单 canary 异常导致的探活失效。

风险：

- 探活流量增加，需要低频、可关闭、可观测。

### P3：切换阻尼，防止域名赢家频繁切换

当前域名缓存 TTL 已有一定阻尼，但在缓存过期或重竞速时，可能因为单次抖动切换赢家。

方案：

- 新代理需要连续赢 2-3 次才替换域名缓存。
- 或者新赢家 EWMA 必须比旧赢家低超过阈值，例如 20% 或 30ms。
- 对 5xx/熔断类故障跳过阻尼，立即切换。

收益：

- 降低出口 IP 抖动。
- 降低登录态、风控、CAPTCHA 相关问题。

适用条件：

- 对 egress 稳定要求高于极致低延迟。
- 已开启会话粘性但仍希望全局域名默认代理更稳定。

### P3：自适应并发限制

在 `ProxySelector` 上增加每代理并发上限：

- 成功且延迟稳定：加性增加上限。
- 超时、5xx、EWMA 快速恶化：乘性降低上限。
- `ordered_proxies()` 过滤达到上限的代理。

收益：

- 防止慢代理在高并发下被请求堆死。
- 比单纯 least-request 更主动地保护上游。

成本：

- 参数复杂，需要较多压测和生产观测。
- 容易把源站慢误判为代理慢，需要与策略路由/多 canary 配合。

## 6. 推荐实施路线

### 第一阶段：不改核心转发，先让现有能力生效

1. 更新 `examples/config.yaml`，补齐速度相关字段。
2. README 增加调参说明。
3. 生产部署开启 `single_send_degrade_fail=2`、`single_send_degrade_ratio=3.0`。
4. 用 `/metrics` 和 `/circuit` 验证：
   - `probes_skipped` 是否为 0 或低值。
   - `racing.amplification` 是否接近预期。
   - `single_send_degrades` 是否在代理波动时增长。

### 第二阶段：策略路由

1. 设计 `PolicyConfig`。
2. 利用现有 `ProxyInfo.tags` 做域名/标签匹配。
3. 让域名缓存、粘性、竞速都遵守策略过滤。
4. 用真实上游压测对比国内/海外/业务域名的 TTFB 和失败率。

### 第三阶段：CONNECT 建链优化

1. 先做观测：补充 CONNECT 新建上游连接计数和 TTFB 分解。
2. 做上游代理 TCP 预热池。
3. 加 fd 预算和空闲超时。
4. 对 HTTPS 短连接场景专项压测。

### 第四阶段：缓存和自适应

1. HTTP 缓存 LRU 和容量上限。
2. 自适应域名 TTL。
3. 多 canary 探活。
4. 视真实瓶颈决定是否做自适应并发限制。

## 7. 压测与验收指标

建议每次优化都至少跑三组：

```bash
python -m bench.stress --quick --rounds 3
python -m bench.stress --mode mixed --rounds 3
python -m bench.stress --mode soak --duration 120 --rounds 3
```

若有真实上游代理：

```bash
python -m bench.stress --upstream real --proxies proxies.yaml --mode mixed --duration 120 --rounds 3
```

核心指标：

| 指标 | 目标 |
| --- | --- |
| TTFB P50/P95/P99 | 下降，尤其是 P95/P99 |
| total latency P95/P99 | 不能因后台清理、缓存或 fd 压力变差 |
| `racing.amplification` | 下降；CONNECT 场景越低越好 |
| `upstream_attempts` | 在成功率不下降的前提下降低 |
| `domain_hit_rate` / `sticky_cache_hits` | 热域名和稳定会话应上升 |
| `http_hit_rate` | 对可缓存 GET 应上升 |
| `proxy_in_flight` / `max_in_flight` | 不应长期集中在慢代理 |
| `circuit_open_count` | 坏代理场景应增长；正常场景不应频繁增长 |
| `probes_skipped` | 长期增长说明 canary 不合适 |
| server loop lag P95/max | 不应显著上升 |
| RSS / fd_peak | soak 下应稳定 |

## 8. 代码级注意事项

- 被竞速取消的候选不能记失败，否则健康慢代理会被误熔断。当前 `_try_http()` / `_try_tunnel()` 已处理，后续改动要保留。
- 竞速赢家只应在确认采用后更新域名 meta，败者只能记 attempted stats。当前 `_record_win_meta()` 的调用位置是正确的。
- 单发降级与熔断要解耦：降级是“不要继续确定性单发”，熔断是“暂时剔除候选”。
- 策略路由必须同时作用于粘性、域名缓存和竞速，否则旧缓存可能绕过新策略。
- HTTP 缓存如果做 LRU，必须同步维护 `_http_cache_domain_index`，否则写方法按域名失效会漏删。
- CONNECT 预热池必须有全局 fd 预算和 per-proxy 上限，不能为了降低 TTFB 引入资源泄漏。

## 9. 优先级清单

| 优先级 | 事项 | 类型 | 预期收益 |
| --- | --- | --- | --- |
| P0 | 生产配置显式开启错峰、熔断、探活、单发降级 | 配置 | 立刻降低坏代理和慢代理影响 |
| P1 | 更新示例配置和调参说明 | 文档/配置 | 减少部署误用 |
| P1 | 策略路由：域名/标签 -> 代理子集 | 开发 | 降低 TTFB、失败率和竞速扇出 |
| P1 | CONNECT 上游 TCP 预热池 | 开发 | 降低 HTTPS 短连接 TTFB |
| P2 | HTTP 缓存 LRU + 总容量限制 | 开发 | 控制内存，稳定高基数流量 |
| P2 | 自适应域名 TTL | 开发 | 稳定域减少竞速，抖动域快速换路 |
| P2 | 多 canary/按标签探活 | 开发 | 提升质量模型可信度 |

| P3 | 自适应并发限制 | 开发 | 高并发下保护慢代理 |
