## 一、auto_squid 现状定位

auto_squid 的选路本质（读 `auto_squid/router.py`）：

| 机制 | 实现 | 对应业界概念 |
| --- | --- | --- |
| 竞速 | `_race` + `_try_http`/`_try_tunnel`：多代理**同时**发，首字节判胜，败者取消 | **Happy Eyeballs 竞速**（RFC 8305） |
| 域名缓存 | `_get_fresh_proxy`（TTL 600s）：域名级"赢家单发" | ECMP/PCC 的流亲和 |
| 会话粘性 | `_sticky_cache`（TTL 1800s 滑动）：客户端+域名级 egress 稳定 | 连接级亲和（PCC/ip-hash） |
| 周期性再评估 | `recheck_hits`：粘性命中 N 次触发探路重竞速 | SD-WAN 周期性再评估 |
| 选择器 | `ProxySelector.ordered_proxies()`：**均匀随机 shuffle，无权重** | 无（无质量模型） |

**已具备**：竞速（延迟最优）+ 流亲和（egress 稳定）。

**缺口**：
- 无主动健康探测（代理死了要等请求失败才知道）
- 无质量模型/权重（EWMA 延迟、失败率不进选择）
- 无全局熔断（死代理每次仍参与竞速，白占竞速槽）
- 无 in-flight 感知（慢代理可能被并发打爆）
- 竞速为"同时全发"，未错峰（CONNECT 隧道扇出浪费）
- 无 slow-start 保护（新加入/刚恢复的代理会被当老成员一样直接吃满流量）
- 无历史 RTT 跨接口失效的边界处理（EWMA 若沿用，代理/网络切换后是陈数据）

## 二、出口路由器/多 WAN 怎么做

| 策略 | 做法 | 来源 |
| --- | --- | --- |
| **per-packet vs per-connection** | per-packet 需要两端同时可控才可靠；只有一端可控（家用/出口侧）必须 per-connection | MikroTik Load Balancing 手册 |
| **ECMP（Equal Cost Multi-Path）** | 多条等价默认路由，**流级哈希**分配（l3=src+dst IP，l4=加协议+端口）；`check-gateway=ping` 失败即从 ECMP 组剔除 | MikroTik IP Settings、多 WAN failover 指南 |
| **PCC（Per Connection Classifier）** | 对五元组哈希取模分桶，把整条连接钉在一条链路上（会话亲和），**新连接才重分配** | RouterOS PCC 文档 |
| **Nth** | 按连接计数取模分发，实现 per-connection 或 per-packet | MikroTik Load Balancing 手册 |
| **策略路由 PBR** | 按源/目的/应用/时间把流量导向指定线路 | MikroTik PCC 手册、FortiGate SD-WAN 规则 |
| **健康探测 + 故障切换** | `check-gateway=ping` / Netwatch / 递归锚点路由；秒级~30s 剔除死链路；主备（distance 不同）或 active/active | MikroTik 多 WAN 对比表 |
| **SD-WAN 路径质量** | BFD hello（默认 1s）持续采 RTT；10min 一个"桶"算平均 **loss / latency / jitter**，超 SLA 阈值就换路/剔除；支持 **dampening**（切换阻尼防抖）与 Load Balance 分摊 | Cisco SD-WAN App-Aware Routing、Cisco BFD 与 AAR、FortiGate Performance SLA |
| **带宽/成本加权** | 按链路带宽（weight）或成本做偏好 | FortiGate SD-WAN 设计 |

**关键对照**：auto_squid 的域名缓存+粘性 ≈ ECMP/PCC 的"流亲和"；`recheck_hits` ≈ SD-WAN 周期性再评估。但它**没有主动探测**（SD-WAN 的 BFD/SLA 那一层）和**切换阻尼**。

**RFC 8305 的精确参数**（下文落地草案直接引用）：
- §4 排序：有历史 RTT 时应加一条"选低 RTT 地址"的排序规则；**RTT 数据不可跨网络接口使用，换网络后应清空**——对 auto_squid：代理分组更换/网络切换后要重置 EWMA，否则拿旧延迟排序。
- §5 错峰：连接尝试**不应同时发起**，应逐个、错开启动（先发最优 1 个，隔一段再发下一个）。默认连接尝试延迟 **250ms**；更细的实现可动态取"上一次尝试开始发第二个 SYN 的时点"（基于 RFC 6298 RTO）；有历史 RTT 可影响该延迟。**下限 100ms**（绝对值下限 10ms，防止丢包率高时拥塞崩溃），**上限 2s**。首个成功即取消其余未开始/未成功的尝试。
- 竞速对象**排序**影响失败者是否白占竞速槽（当前 auto_squid 为均匀随机排序）。

## 三、经典负载均衡算法目录（L4/L7 层参考）

| 算法 | 机制 | 参考 |
| --- | --- | --- |
| RR / WRR / 加权随机 | 轮询 / 按权重轮询 / 按权重随机；Dubbo 默认加权随机，但**慢代理会堆积请求**（打到慢节点就卡住，久而久之全卡上去） | nginx LB、IPVS、Dubbo |
| **Least Connections / Least Time** | 发给在途连接最少 / 平均响应时间最低者；`least_time header` = 首字节时间 | nginx、IPVS `lc` |
| **一致性哈希** | 哈希环（Ketama/Maglev），增删节点只迁移约 1/N | Envoy ring hash / Maglev |
| **P2C（Power of Two Choices）** | 随机抽 2 个选负载低的；最大失衡从 O(log n)→O(log log n) | Envoy P2C、Mitzenmacher、Dubbo |
| **P2C 具体化** | Envoy：默认抽 N=2、比 active requests，权值使 host 权重随在途数下降，抗"羊群效应"（herding） | Envoy 文档（Q=2，`active_request_bias`） |
| **加权 least request（非均匀权）** | 权重按负载动态调：`weight = load_balancing_weight / (active_requests + 1)^active_request_bias`（bias 默认 1.0） | Envoy `LeastRequest` |
| **EWMA / peak EWMA** | 维护 RTT 移动平均（加权在途数），发给成本函数最小者 | Finagle/Linkerd 对比实验 |
| **LeastActive / ShortestResponse（Dubbo）** | 在途最少优先；同值再加权随机；后者用最近 30s 滑动窗平均响应时间排序 | Dubbo 官方文档 |
| **Adaptive（Dubbo）** | 基于 P2C：抽 2 节点，比较"负载"（结合 CPU/内存/延迟等的综合指标）选负载最小者 | Dubbo `AdaptiveLoadBalance` |
| **熔断 / outlier / 自适应并发** | 连续失败开闸 + 指数退避探测；自适应并发限流 | Hystrix、Envoy outlier detection |
| **slow-start** | 节点加入/恢复后从低权重按窗口爬升到满权重（Envoy slow-start，60s 窗口），防止新成员被流量打懵 | Envoy、AWS ALB |
| **Happy Eyeballs（竞速）** | 并行建连、先成者胜；**按历史 RTT 排序候选、错峰启动**（默认 250ms 间隔，下限 100ms，上限 2s；有历史 RTT 时可动态计算到 SYN 重传时延） | RFC 8305 §4-§5 |

## 四、值得 auto_squid 参考的（按价值排序）

> 排序依据既有文档 + 本次补充文献（Envoy / Dubbo / Linkerd / RFC 8305 原文）。
> **实验证据（Linkerd/Finagle）**：11 个后端、单节点人为变慢到 2s 30 秒的模拟里，
> round-robin 在 **95 分位**就扛不住，least-loaded 撑到 **99 分位**，peak EWMA 撑到 **99.9 分位**；
> 以 1s 超时换算成功率约 95% / 99% / 99.9%。——**"信息用的越多，尾延迟越短"**，是本节所有"加权/选优"方案的直接依据。

### P1 —— 最贴合、成本最低，建议直接做

1. **按历史 RTT 排序竞速批次**
   RFC 8305 §4 明确写：有状态客户端应用历史 RTT 优先排序。
   现在 `ordered_proxies()` 是均匀随机——竞速结果不受顺序影响，但**顺序决定谁先到、决定失败代理是否白占一个竞速槽**。维护每代理 EWMA 首字节延迟，排序后再竞速 → 首字节更快、扇出更省。
   **新增约束**（RFC 8305 §4）：历史 RTT 不可跨网络接口使用，换网络后应清空——代理分组/网络切换时要重置 EWMA，否则拿陈旧延迟排序。

2. **全局熔断器 + 指数退避探活**
   Hystrix / Envoy outlier detection。
   现在死代理**每次请求仍会被竞速**，浪费并发槽且拖长失败路径。加：连续失败 N 次 → `circuit_open_until` 指数退避，退避期内不参与竞速；后台探活任务（仿 `_flush_loop`）恢复后放回。

3. **每代理 EWMA 质量 + 加权**
   Finagle peak EWMA / nginx least_time。
   竞速批次用加权随机或"最可能快者靠前"选择，把竞速扇出集中到优质代理。
   **量化**：Linkerd 实验证明 peak EWMA（RTT × 在途数）尾延迟远优于纯 RR/least-loaded，此处"加权选批"把竞速扇出集中到优质代理，是同类收益。

### P2 —— 明显增益，值得纳入

4. **错峰启动**
   RFC 8305 §5：连接尝试**不应同时发起**。先发最优 1~2 个，未胜再间隔补发下一个。**默认 250ms，下限 100ms（绝对值 10ms），上限 2s**；有历史 RTT 时可动态取到"上次尝试 SYN 重传时点"。**极小延迟代价，大幅减少 CONNECT 隧道扇出**（CONNECT 败者隧道要建好再关，最浪费）。

5. **每代理 in-flight 计数 + P2C/least-active 选批**
   Envoy P2C、Dubbo LeastActive、IPVS `lc`：竞速选批时避开在途积压多的代理，保护慢代理不被打爆。
   **Envy 细节**：默认抽 2 个比 active requests；均匀权用 P2C（抗 herding），非均匀权用 `weight/(active+1)^bias`（bias 默认 1.0）动态调权重。

6. **slow-start 保护新代理**
   Envoy slow-start（60s 窗口）：新加入或熔断恢复的代理从低权重开始，随成功次数爬升到满权重。防止新成员被首批流量打懵、进而误判为劣质又被熔断——**和"熔断恢复探活"天然配套**，否则刚恢复的代理可能因冷启动被请求量冲垮。

7. **按目标策略收窄候选集**
   PBR / FortiGate SD-WAN rule：若代理有地域差异，配置"域名模式 → 代理子集"（如国内域名只用国内代理），竞速只在该子集内进行。收益取决于代理地域分布。

### P3 —— 视目标决定

8. **切换阻尼（dampening）**
   Cisco SD-WAN：新代理须连续赢若干次才替换域名赢家，防 flapping。当前域名缓存 TTL 内固定，天然有阻尼，可留待观察。

9. **一致性哈希稳定映射**
   Envoy ring hash / Maglev：仅在"希望跨重启/跨进程 egress 映射稳定"时有意义，与"追求最快"目标略有张力。若走此路，**Maglev 构建/查表比 Ketama 快约 10x/5x**（Envoy 基准），但增删节点扰动约为 ring hash 的 2 倍——换表大小可降扰动。

10. **置信度驱动的竞速 vs 单发**
    UCB/ε-greedy 形式化 `recheck_hits`：把确定性探路升级为"对不确定域多试、对稳定域少试"。收益有限——HTTP 败者在首字节即取消，竞速边际成本本就不高。

### 新补充：两处"参数即算法"细节（选自最新文献）

- **Dubbo 默认是加权随机**，官方文档明确点出缺陷：**慢代理会堆积请求**（打到慢节点就卡住，久而久之全卡上去）。auto_squid 若引入权重，默认策略别选纯加权随机，至少加 in-flight 维度（LeastActive/P2C）。
- **Dubbo ShortestResponse**：以最近 **30s 滑动窗平均响应时间**排序，同值再加权随机——比"瞬时首字节"更抗抖动，可作竞速排序的平滑化替代。

## 五、落地草案

```
Router.__init__ 增加:
  proxy_quality: {pid: {
    ewma_ttfb,        # 成功请求的 EWMA 首字节延迟(RTT ×在途, peak EWMA 可选)
    consecutive_fail, # 连续失败计数 → 熔断触发
    in_flight,        # 当前在途请求数(least-loaded/P2C 选批用)
    probed_at,        # 上次探活结果
    started_at,       # 加入/熔断恢复时刻 → slow-start 计算爬升权重
    circuit_until}}   # 指数退避开闸时间
  后台探活 task(仿 _flush_loop): 每 PROBE_INTERVAL 对 enabled 代理做轻量
  CONNECT 到 canary(如 1.1.1.1:443)+关闭, 计延迟/成败 → 更新 quality;
  连续失败 → 熔断(指数退避); 恢复后 started_at=now → slow-start 低权重爬升

ProxySelector.ordered_proxies() 改为:
  1) 过滤 circuit_until 未到的熔断代理
  2) 按 slow-start 权重 × EWMA(或加权随机)排序/选批, in_flight 参与排序(P2C/least-active)
  3) 分组/网络切换 → 重置全部 EWMA/stats(RFC 8305 §4: 历史 RTT 不跨接口)

_build_racing_tasks_* 改为:
  取前 max_retries 个质量最优, 错峰启动(默认 250ms·下限 100ms/10ms·上限 2s)
  首个首字节成功 → 取消其余

每次 _try_http/_try_tunnel 成败更新 quality:
  EWMA+1 / 失败计数 / in_flight±1 / 成功则降 consecutive_fail 并推进 slow-start
```

**边界与成本**：
- 探测会消耗上游流量/配额 → 间隔可配、可关闭。
- canary 延迟 ≠ 目标站延迟 → 探测只用于**存活 + 粗排序**，域名级最终仍由竞速决定。
- 竞速排序的历史 EWMA **不可跨网络/跨代理分组沿用**（RFC 8305 §4）；切换后清空重学。
- slow-start 的主要成本是"少量流量可能走次优代理"，但避免新代理被冷启动打垮→误熔断的恶性循环。
