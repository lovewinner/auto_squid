## 一、auto_squid 现状定位

auto_squid 的选路本质（读 `auto_squid/router.py`）：

| 机制 | 实现 | 对应业界概念 |
| --- | --- | --- |
| 竞速 | `_race` + `_try_http`/`_try_tunnel`：多代理**同时**发，首字节判胜，败者取消 | **Happy Eyeballs 竞速**（RFC 8305） |
| 域名缓存 | `_get_fresh_proxy`（TTL 600s）：域名级"赢家单发" | ECMP/PCC 的流亲和 |
| 会话粘性 | `_sticky_cache`（TTL 1800s 滑动）：客户端+域名级 egress 稳定 | 连接级亲和（PCC/ip-hash） |
| 周期性再评估 | `recheck_hits`：粘性命中 N 次触发探路重竞速 | SD-WAN 周期性再评估 |
| 选择器 | `ProxySelector.ordered_proxies()`：**均匀随机 shuffle，无权重** | 无（无质量模型） |

**已具备**：竞速（延迟最优）+ 流亲和（egress 稳定）。

**缺口**：
- 无主动健康探测（代理死了要等请求失败才知道）
- 无质量模型/权重（EWMA 延迟、失败率不进选择）
- 无全局熔断（死代理每次仍参与竞速，白占竞速槽）
- 无 in-flight 感知（慢代理可能被并发打爆）
- 竞速为"同时全发"，未错峰（CONNECT 隧道扇出浪费）

## 二、出口路由器/多 WAN 怎么做

| 策略 | 做法 | 来源 |
| --- | --- | --- |
| **per-packet vs per-connection** | per-packet 需要两端同时可控才可靠；只有一端可控（家用/出口侧）必须 per-connection | MikroTik Load Balancing 手册 |
| **ECMP（Equal Cost Multi-Path）** | 多条等价默认路由，**流级哈希**分配（l3=src+dst IP，l4=加协议+端口）；`check-gateway=ping` 失败即从 ECMP 组剔除 | MikroTik IP Settings、多 WAN failover 指南 |
| **PCC（Per Connection Classifier）** | 对五元组哈希取模分桶，把整条连接钉在一条链路上（会话亲和），**新连接才重分配** | RouterOS PCC 文档 |
| **Nth** | 按连接计数取模分发，实现 per-connection 或 per-packet | MikroTik Load Balancing 手册 |
| **策略路由 PBR** | 按源/目的/应用/时间把流量导向指定线路 | MikroTik PCC 手册、FortiGate SD-WAN 规则 |
| **健康探测 + 故障切换** | `check-gateway=ping` / Netwatch / 递归锚点路由；秒级~30s 剔除死链路；主备（distance 不同）或 active/active | MikroTik 多 WAN 对比表 |
| **SD-WAN 路径质量** | BFD hello（默认 1s）持续采 RTT；10min 一个"桶"算平均 **loss / latency / jitter**，超 SLA 阈值就换路/剔除；支持 **dampening**（切换阻尼防抖）与 Load Balance 分摊 | Cisco SD-WAN App-Aware Routing、Cisco BFD 与 AAR、FortiGate Performance SLA |
| **带宽/成本加权** | 按链路带宽（weight）或成本做偏好 | FortiGate SD-WAN 设计 |

**关键对照**：auto_squid 的域名缓存+粘性 ≈ ECMP/PCC 的"流亲和"；`recheck_hits` ≈ SD-WAN 周期性再评估。但它**没有主动探测**（SD-WAN 的 BFD/SLA 那一层）和**切换阻尼**。

## 三、经典负载均衡算法目录（L4/L7 层参考）

| 算法 | 机制 | 参考 |
| --- | --- | --- |
| RR / WRR / 加权随机 | 轮询 / 按权重轮询 / 按权重随机 | nginx LB、IPVS |
| **Least Connections / Least Time** | 发给在途连接最少 / 平均响应时间最低者；`least_time header` = 首字节时间 | nginx、IPVS `lc` |
| **一致性哈希** | 哈希环（Ketama/Maglev），增删节点只迁移约 1/N | Envoy ring hash / Maglev |
| **P2C（Power of Two Choices）** | 随机抽 2 个选负载低的；最大失衡从 O(log n)→O(log log n) | Envoy P2C、Mitzenmacher、Dubbo |
| **EWMA / peak EWMA** | 维护 RTT 移动平均（加权在途数），发给成本函数最小者 | Finagle/Linkerd 对比实验 |
| **熔断 / outlier / 自适应并发** | 连续失败开闸 + 指数退避探测；自适应并发限流 | Hystrix、Envoy outlier detection |
| **Happy Eyeballs（竞速）** | 并行建连、先成者胜；**按历史 RTT 排序候选、错峰启动**（默认 250ms 间隔，下限 100ms，上限 2s） | RFC 8305 §4-§5 |

## 四、值得 auto_squid 参考的（按价值排序）

### P1 —— 最贴合、成本最低，建议直接做

1. **按历史 RTT 排序竞速批次**
   RFC 8305 §4 明确写：有状态客户端应用历史 RTT 优先排序。
   现在 `ordered_proxies()` 是均匀随机——竞速结果不受顺序影响，但**顺序决定谁先到、决定失败代理是否白占一个竞速槽**。维护每代理 EWMA 首字节延迟，排序后再竞速 → 首字节更快、扇出更省。

2. **全局熔断器 + 指数退避探活**
   Hystrix / Envoy outlier detection。
   现在死代理**每次请求仍会被竞速**，浪费并发槽且拖长失败路径。加：连续失败 N 次 → `circuit_open_until` 指数退避，退避期内不参与竞速；后台探活任务（仿 `_flush_loop`）恢复后放回。

3. **每代理 EWMA 质量 + 加权**
   Finagle peak EWMA / nginx least_time。
   竞速批次用加权随机或"最可能快者靠前"选择，把竞速扇出集中到优质代理。

### P2 —— 明显增益，值得纳入

4. **错峰启动**
   RFC 8305 §5：现在 `max_retries` 个代理同时发；改为先发最优 1~2 个，未胜再间隔 ~50ms 补发下一个。极小延迟代价，**大幅减少 CONNECT 隧道扇出**（CONNECT 败者隧道要建好再关，最浪费）。

5. **每代理 in-flight 计数 + P2C/least-active 选批**
   Envoy P2C、Dubbo LeastActive、IPVS `lc`：竞速选批时避开在途积压多的代理，保护慢代理不被打爆。

6. **按目标策略收窄候选集**
   PBR / FortiGate SD-WAN rule：若代理有地域差异，配置"域名模式 → 代理子集"（如国内域名只用国内代理），竞速只在该子集内进行。收益取决于代理地域分布。

### P3 —— 视目标决定

7. **切换阻尼（dampening）**
   Cisco SD-WAN：新代理须连续赢若干次才替换域名赢家，防 flapping。当前域名缓存 TTL 内固定，天然有阻尼，可留待观察。

8. **一致性哈希稳定映射**
   Envoy ring hash：仅在"希望跨重启/跨进程 egress 映射稳定"时有意义，与"追求最快"目标略有张力。

9. **置信度驱动的竞速 vs 单发**
   UCB/ε-greedy 形式化 `recheck_hits`：把确定性探路升级为"对不确定域多试、对稳定域少试"。收益有限——HTTP 败者在首字节即取消，竞速边际成本本就不高。

## 五、落地草案

```
Router.__init__ 增加:
  proxy_quality: {pid: {ewma_ttfb, consecutive_fail, in_flight, circuit_until}}
  后台探活 task(仿 _flush_loop): 每 PROBE_INTERVAL 对 enabled 代理做轻量
  CONNECT 到 canary(如 1.1.1.1:443)+关闭, 计延迟/成败 → 更新 quality;
  连续失败 → 熔断(指数退避)
ProxySelector.ordered_proxies() 改为: 过滤熔断代理 → 按 EWMA 排序(或加权随机)
_build_racing_tasks_* 改为: 取前 max_retries 个质量最优, 支持错峰启动
每次 _try_http/_try_tunnel 成败更新 quality(EWMA +1、失败计数、in_flight±1)
```

**边界与成本**：
- 探测会消耗上游流量/配额 → 间隔可配、可关闭。
- canary 延迟 ≠ 目标站延迟 → 探测只用于**存活 + 粗排序**，域名级最终仍由竞速决定。
