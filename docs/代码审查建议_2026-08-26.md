## 第一优先级 — 一个已上线但生产上"没生效"的功能

### #1 refill 空闲暂停在生产上从未触发(opt.log 一手验证)→ 已决定废弃(接受空转)

> **2026-08-26 二次分析结论**:此前建议"降 `refill_pause_minutes` 到 15–20"**已被实测推翻**。
> 深夜簇间隔中位数仅 5 分钟,即使把阈值降到 15 分钟同样捕不到这些 2–5 分钟的脉动——
> 参数上抠不出解。经与用户讨论,决定**放弃活动检测,接受深夜空转**。见下"结论"。

- **现象**:`refill_pause_minutes=60` + `refill_pause_activity_window=120` + `refill_pause_min_requests=3` 已部署。
  opt.log 跨午夜数据(8/25 16:20 → 8/26 15:07,含 00:00–07:59 完整 480 采样点)显示
  `conn_pool_idle_paused` **全程 False(0/480)**;深夜(00:00–07:59)`conn_pool_creates` 仍 250–310/小时,
  `target_pool_creates` 56–65/小时,`pool_size` 恒 10–12。
- **根因(第二次分析挖到底)**:深夜请求不是零,而是以 **2–5 分钟一簇**规律到来(`clients2.google.com`/
  `clients2.googleusercontent.com` CONNECT,日志显示 `all proxies failed`,即 Android 推送心跳失败重试)。
  28 个 ≥3 请求簇横贯 02–07:59(中位间隔 5 分钟,最大才 60 分钟)。`_record_request_activity` 的滑动窗口
  (120s 内 ≥3)`router.py:2082-2120` 被持续满足 → `_last_request_activity` 一直被刷新 →
  `now - last_activity >= 60min`(`2122-2136`)永远不成立。**持续低活动让"第 N 分钟无活动才暂停"模型失效。**
- **空转成本实测(02:00–07:59, 359 采样点)**:通用池建连 1607→过期 1290(80%)、目标池 349→345(98%)。
  **但通用池瞬时峰值仅 12 条**(6 代理 × refill_target=2,< budget 64)——所谓"6h 白建 ~2000 条"意味着
  同时只存在 ≤20 条 TCP,是"每 5s 重连一次的小脉冲",不是并发轰炸。省这组 12 条夜里又被心跳打穿的
  预连接,不值得;refill 每周期几十次建连失败 log 亦可忽略。
- **结论(已定)**:为捕不准夜间活动、维护成本高的暂停逻辑(`silence_sec` 弃用、簇度判定、黑名单的利弊),
  不值得。**已按用户决定落地**:`config.yaml` 置 `refill_pause_minutes: 0`(明确"不暂停",保留机制供明确
  零流量场景启用)。机制保留、字段保留、回归测试保留,只是生产不再配置。若未来出现真正零流量的夜间
  (如固定无人值守时段),可重新评估"固定时钟窗口"方案。
- **遗留可选优化**(未做):深夜心跳(`clients*.google.*` 等)每 2–5 分钟一簇,触发的 CONNECT 竞速失败
  会产生日志噪音与无效尝试,可考虑在客户端侧过滤目标或调熔断参数——超出本次范围。

## 第二优先级 — 正确性 / 资源泄漏隐患(均经人工复核)

### #2 `_established_pool` 不受 fd 预算约束 + 复用半开连接会"赢"竞速却不兜底 → ✅ 已修复

> **2026-08-26 已修复**:新增 `_ESTABLISHED_KEY_CAP=2`(per-key 上限,与 target_pool 对齐)与
> `_ESTABLISHED_PROBE_TIMEOUT=0.05s`。归还路径(`_relay_tunnel`)加全局预算(`conn_pool_total`,三池
> 同口径)+ per-key cap 检查,超限 close 不复用;两处 refill 预算快照纳入 `_established_pool`;新增
> `_established_alive`(read(1)+超时探活)在 `_try_tunnel` 复用前判死,FIN→b''/RST→异常 均判死并回落
> 新建,杜绝"死隧道 1 tick 赢竞速";归还连接设 `SO_KEEPALIVE`(见 #5)。新增 4 个测试(三态探测 /
> cap 并发 / 预算注入 / keepalive),171 全过。

- **定位**:`router.py:3337-3341` 归还已握手隧道时只做了脏缓冲检查,**既没查 `conn_pool_total` 全局预算,
  也没设单键上限**(对比 `_target_pool` 有 `cap=2`)。fd 预算快照(`2151-2152`、`2194-2195`)只对
  `_conn_pool + _target_pool` 求和,根本没数 `_established_pool`。
- **后果 1(fd 无界增长)**:CONNECT 突发时同一 `(proxy,target)` 可堆很多条全双工 socket,只在
  prune 周期满后才回收。
- **后果 2(死隧道赢得竞速)**:`_try_tunnel` 复用路径(`2764-2794`)跳过 CONNECT 握手、无任何 I/O,
  一个事件循环 tick 就完成 → **必然赢过**所有正在做 15s CONNECT 的活候选。而 `_established_pool_peek`
  的"干净"检查(`2070` 只看 `reader._buffer`/`at_eof()`)查不出半开连接(对端 RST 但无 FIN)。
  结果:客户端拿到 `200` 后接一条死管道,`_handle_connect` 已 return,**没有回退/重试**。
- **修法**:归还路径加 `cap` + 预算检查(超限就 close 而非归还);复用前做廉价活性探测(短超时 read
  期待 EOF,或对该池连接统一开 `SO_KEEPALIVE`,见 #5)。
- **备注**:memory 记录 "established_reuse 未配置",当前生产**休眠中**——已修复,**修复后启用是安全的**。

### #3 `_race_staggered` 全失败时泄漏 5xx 流式 resp(已复核 `2420-2493`)→ ✅ 已修复

> **2026-08-26 已修复**:`return winner`(全失败走到底)之前补 `if completed and cleanup:
> self._spawn_cleanup(completed, cleanup)`,把持有 5xx resp 的 completed 候选下放清理。
> 回归测试:`test_all_fail_triggers_cleanup`(全 5xx → cleanup 一次性覆盖 2 个候选并 aclose)+
> `test_winner_path_also_cleans_losers`(赢家路径不破坏)。

- **定位**:`_race_staggered` 只在 `winner is not None` 分支(`2487-2488`)调用 `_spawn_cleanup`。当所有
  候选都失败、循环走到底 `return winner`(此时为 None,`2493`)时,`completed` 里那些"拿到 5xx 响应头
  但被判非胜"的任务**持有的 `resp` 没人 `aclose()`**,占着 httpx 连接池连接(每代理上限 200),反复
  全失败会耗尽连接池。
- **修法**:`2493` 之前补 `if completed and cleanup: self._spawn_cleanup(completed, cleanup)`。

### #4 `_forward_single` 的 `resp.aclose()` 不在 finally(已复核 `3079-3083`)→ ✅ 已修复

> **2026-08-26 已修复**:`_stream_upstream_response` + 缓存写入 + `return` 收进 `try`,`resp.aclose()`
> 收进 `finally`——即使 stream 抛 `BaseException` 也释放池化连接。回归测试:
> `test_stream_raise_still_aclose`(stream 抛 CancelledError → aclose 仍被调)。

```python
try:
    buffered = await self._stream_upstream_response(writer, resp, method, url)
    if buffered is not None and resp.status_code in CACHEABLE_STATUS:
        self._http_cache_set(...)
    return resp.status_code
finally:
    try:
        await resp.aclose()
    except Exception:
        pass
```

- **风险**:`_stream_upstream_response` 内部 catch 很宽,但若抛 `BaseException`(MemoryError/KeyboardInterrupt
  等),`resp.aclose()` 被跳过,池化连接泄漏。
- **修法**:把 `aclose()` 挪进 `finally`。

## 第三优先级 — 健壮性(DoS / 数据正确性)

### #5 半开连接探测缺失:`_set_nodelay`(`1803-1815`)只设 `TCP_NODELAY`/`TCP_QUICKACK`,从不设 `SO_KEEPALIVE` → ✅ 已修复

> **2026-08-26 已修复(随 #2)**:新增 `_set_pool_keepalive`(SO_KEEPALIVE + TCP_KEEPIDLE=60s +
> TCP_KEEPINTVL=10s),`_relay_tunnel` 归还 established 池时调用。OS 在驻池期间判死纯半开,
> 补足 `read(1)` 探测查不出的静默对端。

- **风险**:池化上游连接对端悄悄死掉(无 FIN/RST)时,`_buffer`/`at_eof()` 查不出来,要等 `_pipe` 的
  300s 硬超时(`2597`)才发现。
- **修法**:给池化连接(尤其 `_established_pool`)加 `SO_KEEPALIVE`(+`TCP_KEEPIDLE=60`/`TCP_KEEPINTVL=10`),
  OS 会在 ~90s 内检测半开并送 EOF,远快于 300s。

### #6 `handle_client` 读请求头无上限(`2830-2835`)

- **风险**:每行被 readline 的 64KB 限,但**行数无上限**。慢速 loris 式攻击发大量小 header 行会让
  `headers` bytearray 无界增长。
- **修法**:加 header 数量(如 100)和总字节(如 1MB)上限,超限返回 431。

### #7 截断响应被当完整响应转发(`_stream_upstream_response` `3200-3243`)

- **风险**:上游 `Content-Length` 声明 N 但实际发 <N 字节时,循环提前结束、不写结束标记也不报错,客户端
  拿到一个"承诺 N 字节却少给"的响应会挂到自己的超时。
- **修法**:累计流式字节,结束后若 `streamed != upstream_cl` 就关连接或回退 chunked,至少记 warn。

### #8 聚合去重超时 100ms 形同虚设(`_AGG_WAIT_TIMEOUT=0.1`,`3020`)

- **风险**:100ms 比典型上游 TTFB 还短 → 并发相同 GET 几乎都会超时回退竞速,**去重等于死代码**,缓存
  未命中时对热门接口形成 stampede(还会通过 `_record_attempt` 扇出误触熔断)。
- **修法**:把超时提到秒级,或把 future 改在"首字节/响应头到达"时 resolve(而非整个 body 流完后)。

## 第四优先级 — 安全(管理面板)

### #9 仪表盘存在存储型 XSS(已复核 `api.py:462-469, 510-521`)

- **风险**:`domain`/`client IP`/`pid` 来自客户端可控的 CONNECT 目标,却通过模板字符串拼进 HTML 直接
  `innerHTML`。客户端发 `CONNECT <img src=x onerror=...>:443` → 任何在浏览器看 `/` 的运维中招。
- **修法**:加 `esc()` 转义,或用 `textContent`/DOM 构建。

### #10 管理 API 默认 `0.0.0.0` + 默认无认证 + 破坏性端点无确认(已确认 `config_schema.py:31,68`)

- **风险**:`POST /proxies`、`POST /quality/reset`、`POST /circuit/reset` 任意网络可达者可调用,且
  `/stickiness` 泄露 client-IP→出口代理映射。
- **修法**:`APIConfig.host` 默认改 `127.0.0.1`;`api.auth.enabled=False` 且 host 非 loopback 时拒绝启动。

### #11 `proxy_store.save()` 全仓零调用者(已 grep 确认)

- **风险**:`POST /proxies` 只改内存 → 重启即丢。运维以为 API 加的代理已保存,其实没有。
- **修法**:API 改动后落盘(且用 temp+`os.replace` 原子写、文件 `0600`),或明确文档标注"临时生效"。

## 第五优先级 — 配置层(两条各几行,杠杆最高)

### #12 全局缺 `extra="forbid"` + 零跨字段校验(已 grep 确认)

- **风险**:pydantic 默认忽略未知键 → `stagger_inital:` 这种拼写错误或升级后改名静默落默认,运维无感知。
- **修法**:给 `Config`/`RouterConfig`/`ConnPoolConfig`/`CircuitConfig` 加
  `model_config = ConfigDict(extra="forbid")`,把静默错配变启动报错。同时补 `@model_validator(mode="after")`:
  `target_prewarm`/`established_reuse` 依赖 `conn_pool.enabled`、`stagger_initial<=max_retries`、
  `adaptive_ttl.min<=max`、`concurrency_limit.min<=initial<=max`。

### #13 `logging.level` 配置被忽略(已确认 `cli.py:46-79`)

- **风险**:`LoggingConfig.level` 存在但 `setup_logging` 全部硬编码级别,设 `DEBUG` 没反应。`cli.py:33-43`
  的配置加载也无友好错误(缺失/语法错直接抛 traceback)。
- **修法**:用 `cfg.logging.level` 设文件 handler 级别;配置加载包 try/except + `sys.exit(2)`。

## 第六优先级 — 可维护性(router.py 3557 行的 god-object)

### #14 把 Router 按状态簇拆成协作对象

`Router.__init__`(`516`,单行 ~55 个 kwarg)和 `snapshot_counters`(`1336`,67 行大字典)是状态放错对象的
典型症状。`ProxySelector`(`153-508`)已经证明"抽小类"在这套代码里 work。按收益排序:

| 拆出模块 | 行数 | 价值 |
|---|---|---|
| `pools.py`(`ConnectionPools`) | ~420 | **最高**——三池统一成 `Pool` 类,顺带消灭 #2 的重复 + 把 idle-pause/refill 变成可单测 |
| `domain_cache.py`(+SQLite 持久化) | ~250 | 高 |
| `sticky.py` / `http_cache.py`(+去重) | 各 ~150-200 | 高,纯 |
| `selector.py` / `policies.py` | 小 | 平移即可,低风险 |

拆完后 Router 缩成 ~200 行编排器,`__init__` kwarg 自然分散到各协作类构造函数。

### #15 cli.py 的 ~55 kwarg 手工透传(`93-153`)是纯样板

Router 内部读取,删掉这块手工映射。
