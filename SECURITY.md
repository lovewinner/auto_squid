# Security & Credentials

This document summarizes secure practices for storing proxy credentials and protecting the management API.

1) Default deployment model
- Management API is bound to 127.0.0.1 by default. No remote access unless explicitly enabled with a configuration flag.
- Credentials (proxy username/password) are not stored in plaintext in version-controlled files. By default, proxies.yaml may include proxy metadata but leave sensitive fields blank.

2) Recommended credential storage options

A) OS Keyring (recommended for desktop users)
- Use the `keyring` Python library to store credentials securely in system keychains.

Example (Python):

```python
import keyring
# store
keyring.set_password("auto-squid", proxy_id, password)
# retrieve
pwd = keyring.get_password("auto-squid", proxy_id)
```

B) Encrypted config file
- Use `cryptography.Fernet` or libsodium to encrypt sensitive fields in proxies.yaml. The app prompts for a master password on startup or reads it from an env var.
- Example workflow:
  - `auto-squid encrypt-creds --in proxies.yaml --out proxies.enc --master-pass`
  - `auto-squid start --creds-file proxies.enc`

C) In-memory only
- For ephemeral sessions, accept credentials via CLI or environment and keep them only in memory without writing to disk.

3) Management API authentication
- If remote binding is enabled, require token-based auth.
- Tokens are generated by `auto-squid token create --name <label>` and stored as hashed values in the config DB.
- Example header: `Authorization: Bearer <token>`

4) Audit & logging
- Log administrative actions (create/update/delete proxy, token operations) to an audit log with structured JSON fields: timestamp, actor (if auth), action, resource, client_ip, result.

5) Least privilege and hardening
- Run the service as a dedicated user account.
- Only allow file access to config and DB files by that account.
- For system services (systemd), use systemd's sandboxing features (ProtectSystem, PrivateTmp, NoNewPrivileges).
